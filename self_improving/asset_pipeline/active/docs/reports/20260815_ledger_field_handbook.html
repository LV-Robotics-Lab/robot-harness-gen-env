账本字段手册

每个资产入库时写一份 ledger.json（账本）——它是这个资产在系统里的唯一权威记录。本手册按字段组解释每个属性是什么、为谁存在、缺了会怎样；提供一份可直接照抄的标准 JSON 参考；最后一章讲仓库各管线环节（环境生成、运行时、迁移等）如何与账本对齐。案例均摘自库中真实账本。

30 秒总览：一份账本长什么样 标准 JSON 参考（可直接照抄） 身份与语义 — 检索靠什么找到它 外观（模型级实测） 尺寸决议 — 沙发电视为何都像篮子大 物理放置 — 摆得稳、装得下 物性信封 — 测的还是猜的 表示层 — 同一资产的多副面孔 来源与许可 验证记录 — usable 的唯一来源 仓库各管线环节的对齐指南 已知边界与改进方向

30 秒总览：一份账本长什么样

data/asset_library/302_bowl/ledger.json        ← 每资产一份，git 管辖
{
  "schema_version": "asset_ledger.v3",
  "asset_id": "external_302_bowl",             ← 账本身份
  "external_ids": {"env_gen": "302_bowl"},     ← 目录/IR 侧叫什么
  "category": "bowl",  "kind": "rigid",  "profile": "sapien_only",
  "semantics": { aliases / colors / materials / identity … },
  "models": [ {                                 ← 同一资产可有多个 model
      "model_id": 0,
      "appearance":  { 实测颜色 … },
      "physical":    { 尺寸/姿态/放置/质量摩擦 … },
      "representations": [ GLB / USD 各后端文件 … ],
      "source":      { 从哪下载 or 怎么生成 + 许可 },
      "verification":[ 每后端每检查一条记录 … ]
  } ]
}

贯穿全文的两条设计原则：①谁读它——每个字段必须有真实的代码消费者，否则不进契约（v3 删掉了 9 个无人读取的字段）；②测量带戳——任何实测数字都是"资产 × 测量栈"的属性而非资产固有属性，必须带 measured_against 说明在哪个仿真栈上测得（同一网格换加载器后停留高度可差 9mm）。

身份与语义 — 检索靠什么找到它

asset_id / category / semantics.aliases

必填读者：grounding 匹配

检索匹配依据：prompt 里的物体词与 category 精确相同得 100 分、与别名相同得 90 分。别名解决同物异名（杯子带 ["cup","mug"]，说 mug 也能命中；垃圾桶若只叫 dustbin，搜 "trash can" 就是零命中）。别名是入库时的一次性成本，检索时免费。

external_ids

必填（v3 新增）读者：迁移引擎账本查找

同一资产在不同层名字不同：账本叫 external_302_bowl、目录叫 302_bowl、IR 里可能被标识符消毒成 asset_302_bowl_m0。这个字段把映射写成数据；此前靠代码猜前缀，猜错一个前缀迁移覆盖率就从 100% 掉到 0%。

kind / profile

必填读者：验证门选择 / 跨后端债务检查

kind（rigid/articulated）决定资产要过哪种物理验证（刚体过沉降、关节体过关节扫描）。profile 声明用途：cross_backend 的资产"欠"一份 Isaac 表示与惯量键位，欠着不还会持续显示未达标——声明的债务不会静默消失。

semantics.identity{basis, evidence}

必填

"它是个碗"这个身份声明由谁做出：人工清单（manifest_human）、采购请求（requested_by_acquire）、VLM 看图验证（vlm）。身份出错时可以追溯到声明通道。

外观（模型级实测）

models[].appearance

有测量才写读者：fragment 投影 → grounding 颜色门

颜色不是人标的：模型离屏渲染 4 视角、逐像素投票到 10 个规范色（见 JSON 参考里的 302_bowl：brown 占 79.1%）。发布规则刻意保守——该资产所有可用 model 颜色一致时才对外发布，因为上游检索对"声明了颜色但不匹配"直接拒绝，标错一个颜色等于让资产从此搜不到。

放在 model 级而非资产级的原因：110_basket 有黄/红/白三只篮子（三个 model），资产级只能写"未知"，model 级实测让"红色篮子"能选中红的那只。实测效果：接入 model 级颜色后，44 条检索矩阵的颜色真命中 9 → 23。

尺寸决议 — 沙发电视为何都像篮子大

physical.size_resolution

scale + actual_max_dim_m 必填读者：尺寸不变量校验
真实案例 · 365_tv（自动采购的电视）
"size_resolution": {
  "mode": "absolute:0.25",          ← 采用的决议策略
  "actual_max_dim_m": 7.733635,     ← 原始素材实测最长边：7.7 米！
  "scale": 0.0323263,               ← 施加的缩放
  "reference_max_dim_m": 0.25,      ← 目标：最长边 0.25 米
  "verdict": "scaled"
}

沙发和电视都"篮子大"正是这个字段的现状策略所致，而且是刻意的。网络素材的作者尺度不可信（这台电视素材 7.7 米，也出现过 13.6 米的纸巾盒）；缺口采购的默认策略把最长边压到 0.25 米——保证放得进 0.70×0.50 米桌面工作区的保守值。代价：自动采购的资产趋向同一尺寸，类目间相对比例丢失（真实世界电视≈篮子×2，沙发≈篮子×8）。

三种决议模式都留痕：absolute:X（钉死最长边）、reference（参照库内同类先例，reference_assets 记参照对象）、素材尺度可信时 scale=1 原样通过。改进方向见最后一章。这个字段同时是安全闸：校验器强制 max(mesh_bbox_m) == actual_max_dim_m × scale，历史上一批 39 个资产里抓出 12 个单位漂移（厘米当米）。

物理放置 — 摆得稳、装得下

physical.conventions.stable_poses[]

必填读者：场景求解器生成姿态

物体以什么姿态稳定立在桌上（四元数 + 默认位标记）。声明无免检：即使上游带了姿态声明，校准也会按声明位姿真实放置一次、要求它停住，停不住就用实测姿态替换——上游声明可以让原点悬空 3.5cm，场景一生成就翻倒。measured_against 必填：库里曾同时存在两种互斥姿态方言（上游 identity 与外部 X90），没有字段判别时迁移方拿错方言物体就横躺。

physical.placement

有实测才写（v3 新增）读者：包含检查 / 容器选型

可放置性几何：顶面平的还是空腔（verdict: flat/hollow/unsupportive）、空腔实测内径与腔底高度。腔底测法：用与腔体同量级的载荷实测停留高度再减 5mm——细探针会掉进网格缝隙量出真实物体到不了的深度，照那个数生成会把物体楔进缝里、把容器撬翻。

z_policy / footprint_shape / is_static

必填

z_policy 说清网格原点在哪（底部/几何中心）——原点在中心的物体按"原点贴桌"生成会半埋进桌面，被解算器弹飞。

物性信封 — 测的还是猜的

mass_kg / friction / restitution / inertial

mass/friction 必填restitution/inertial 可选

三态设计（known / estimated / unknown）是本契约在业界没有对应物的部分：YCB 实测过质量、GSO 一半称重一半估算，但没有一家把"这个值是测的还是猜的"写进元数据。对 sim2real 归因这是关键信息：两个后端对"推不推得动"意见不合时，第一件事就是查这里。status=known 但值为空、或 estimated 没写估计器，校验器都拒。

v3 起摩擦拆 static/dynamic（UsdPhysics/KHR/SDF 均为双系数），restitution 留三态位；惯量数值可选、但 cross_backend 资产必须带键——"引擎会从碰撞几何推导"是完整且诚实的答案。

表示层 — 同一资产的多副面孔

representations[]

必填（至少一个 sapien 表示）读者：迁移引擎选文件 / 审计验完整性

同一个 model 在不同后端是不同文件，且是几何上不同的物体：SAPIEN 的 GLB（Y-up、缩放已烘入）与 Isaac 的 USD（Z-up、缩放未烘入）。frame 与 geometry_state 把差异写成数据；迁移引擎的缩放中和只在 scale_baked: true 声明存在时执行——此前按"USD 都烘好了"假设统一中和，物体在 Isaac 里会大 1/scale 倍（实测 2.85×）。

sha256 承担三重职责：文件完整性（审计）、验证防漂移（旧网格的通过记录带不进新网格）、跨机搬运核对。多文件资产（USD payload、MuJoCo OBJ+分解碰撞）用 files[] 逐文件带哈希。

来源与许可

source（retrieved / generated 两个互斥分支）

必填读者：幂等去重 / license 闸

下载分支：(library, group, file) 三元组是再导入的去重键，retrieved_at 记录时点。生成分支：tool/model 及版本、input、seed、params、generated_at——复现一次生成所需的全部。两分支互斥且各有必填集，校验器会抓"从邻居账本复制粘贴只改一半"的混搭。

许可是"不可恢复捕获"：条款页会改版会消失，入库那一刻不记就永远失据，因此任何 profile 下都必填。生成资产的许可是其生成模型的输出条款，不是"没有"。attribution（署名，CC-BY 法律要求）供发布打包时生成 NOTICE。

验证记录 — usable 的唯一来源

verification[]

必填读者：usable 推导（禁止手写）/ fragment 准入

资产"能不能用"不由任何人手写，由验证记录推导：按 (backend, check) 取最新一条，且 verified_digest 必须等于当前网格哈希——换了网格，旧的通过作废。每个后端独立记录：SAPIEN 里稳不代表 Isaac 里稳（接触模型不同）。这套"行为级、按后端、防漂移"的验证账在业界没有先例（业界只有格式校验且不回写元数据），是本契约最值得保留的设计。

仓库各管线环节的对齐指南

总原则：账本是唯一权威，其余环节都是投影或消费——不直接改账本内容，需要新事实时把它写进账本再投影。按仓库真实管线环节逐一说明：

① 环境生成（scene_gen/：parser → grounding → solver → resolved_scene）

消费什么：不直接读账本，读 asset_catalog.json（运行时目录）。账本 → gen_fragment 投影 → s9 合并 → catalog 的链路已把这些字段送到环境生成手上：

  • category/aliases/colors/materials → grounding 的类目与属性匹配；
  • stable_poses/z_policy/footprint → solver 的姿态与占地计算；
  • placement（内腔/支撑面）→ inside/on-top 关系的可解性判断；
  • dimensions（由 mesh_bbox×scale 投影）→ 放置边界与工作区可行域。

对齐要点：环境生成新增可检索属性（如形状词、尺寸档）时，不要在 catalog/overrides 手写——把事实来源定在账本（新字段或 appearance/placement 扩展），投影和消费同一批落地。教训：materials 曾"账本在写、投影缺失"，材质检索空转一周无人发现。

② 运行时回放与校验（script/run_scene_runtime.py）

消费什么：resolved_scene（已含从 catalog 解析的姿态/内腔/尺寸）+ catalog（包含检查读 interior 边界）。对齐要点：运行时发现的资产级问题（持续晃动、包含失败）应回流为账本世界的事实——走 runtime_revocations 或直接的 verification 记录，而不是只在运行时黑名单里打补丁；否则账本以为资产健康、视图层却在悄悄否决它。

③ 资产采集（1_asset_reuse/：检索 → 验证 → 转换 → 入库）

唯一写入方。守则：永远经 ledger.upsert_model 写入（别手拼 JSON）；写完跑 validate_ledger；实测数字必带 measured_against；表示文件写实测的 frame/geometry_state；删资产走 retire_asset（裸 rm 会留下指向空文件的账本条目）。

④ 跨仿真器迁移（shared/openxsim + 2_sim_migration）

消费什么：external_ids（账本查找键）、representations[]（按 backend/role 选文件，按 scale_baked 决定缩放处理）、verification[]（按目标后端查既有验证）。对齐要点：新后端接入三件套——BACKENDS 枚举加名、该后端的 representation（多文件用 files[]）、该后端的 verification 记录；验证回写是义务：E2E 跑通必须回写 verification[]，"跑通但没回写 = 没跑完"（当前 isaacsim 记录为零，是排期中的欠账）。

⑤ Studio 与演示（web/、apps/、demo/）

消费什么：catalog 的可用性与解锁清单（由账本 verification 推导）、运行产物。对齐要点：前端展示"这个资产为什么不可用"时直接引用推导出的 missing 列表，不要另建状态；用户输入在管线入口统一做 Unicode 空白归一（已落地），前端无需自行清洗。

⑥ RoboTwin 任务执行与数据采集（external/RoboTwin）

消费什么：经 shadow 树拿到的资产文件与 overrides（源头同样是账本投影 + 上游手声明）。对齐要点：上游 RoboTwin 自带的资产（001-2xx 原生件）事实以上游声明优先、账本实测兜底；给上游提改动（如 settled 判据、关节单位）走对齐清单，不 fork 语义。

新流程接入 checklist（写给未来的新环节）

  • 要读资产事实：从 catalog / fragment / IR 读投影，不直接解析账本（投影层保证了验证过滤与优先级合并）；确需账本级细节（如验证历史）再读账本；
  • 要写新事实：先问"谁读它、缺了怎么失败"——有真实读者才提字段；经 upsert + validate 写入；实测值带 measured_against；
  • 要换栈（新机器/新加载器/新后端）：物理实测不跟资产走，跟"资产×栈"走——按新栈重跑测量链（校准→探针→颜色，全部可断点续跑，约 1 小时 GPU），产物提交 git。
